# 审计基感知（Audit Basis Sense）

一个教 AI 用向量空间思维分析审计工作簿的方法论 skill。核心理念来自审计一线实践：
**基变换（降维/融合）→ 降低信息熵 → 降低审计时间复杂度**。

本 skill 的路径全部相对于项目根目录 `<unit>/`。

---

## 1. 核心理论：审计时间复杂度

### 1.1 两个交互原子

审计工作中的所有操作，最终都可以拆解为两个基本原子：

| 原子类型 | 符号 | 定义 | 审计例子 | 复杂度 |
|----------|------|------|----------|--------|
| **界面交互原子** | A_ui | 一次鼠标/键盘/API 操作。只要工具支持批量，无论数据是 10 行还是 10 万行，耗时都是 **1 个单位** | 拖拽填充柄到底、Ctrl+C/V、运行脚本 | **O(1)** |
| **认知判断原子** | A_cog | 一次需要人脑/AI 推理的判断。数据增加一行，判断就实打实增加一次 | 肉眼核对金额、阅读摘要判断风险、AI 逐条分类 | **O(N)** |

### 1.2 审计 O 与计算机 O 的区别

| 操作 | 计算机大 O | 审计大 O | 为什么 |
|------|-----------|---------|--------|
| VLOOKUP 匹配 5000 行 | O(N²) | **O(1)** | 人只拖一下填充柄 |
| 肉眼逐行核对 5000 行 | O(N) | **O(N)** | 每行一次认知判断 |
| 复制粘贴 10 万行 | O(N) | **O(1)** | 人只 Ctrl+C/V 一次 |

**关键洞察**：审计时间复杂度由**人的原子操作数量**决定，不由计算机的算法复杂度决定。

### 1.3 审计 O 的极限

审计时间复杂度**最大仅为 O(N) 或 O(KN)**。原因是：

- A_ui（界面交互）天然是 O(1)——工具批量处理
- A_cog（认知判断）最高是逐行逐笔核对——O(N)
- 物理世界不允许指数爆炸——你不可能对 10 万行做 O(N²) 次人脑判断

**所以优化的核心策略是：把 A_cog 尽可能转化为 A_ui。**

## 2. 向量空间模型

### 2.1 工作簿 = 向量空间

一个 Excel 工作簿（.xlsx）就是一个**向量空间**：

- 每个 **sheet** → 一个向量
- 向量的**分量** → `[sheet名称, 列名1, 列名2, ..., 列名K]`
- 空间的**维度** → 由列的集合（基）决定

例如，存货底稿的 3 个 sheet：

```
原材料计价测试 → [原材料明细表, 期初金额, 本期增加, 本期发出, 期末余额]
半成品计价测试 → [半成品明细表, 期初金额, 本期增加, 本期发出, 期末余额]
库存商品计价测试 → [库存商品明细表, 期初金额, 本期增加, 本期发出, 期末余额]
```

### 2.2 Sheet 内部也是一个子空间

一个 sheet 有 N 行 K 列——转置后就是 K 维空间中的 N 个向量。

- 序时账 10 万行 × 4 列 → 4 维空间中的 10 万个向量
- 10 万个向量**共享同一个基**（记账日期、摘要、借方金额、贷方金额），所以可以用统一的线性映射处理

### 2.3 异构 Sheet 的根源

3 个存货 sheet 的差异本质上是什么？**只有第一列名不同，核心列（金额列）完全相同。**
它们没合并成 1 个 sheet 的原因仅仅是：第一列名（sheet 名的具象化）不同。

**关键识别 question**：当你看到多个 sheet，问自己——
> 这些 sheet 的列结构，除了 1-2 列不同以外，其余列是否相同？

如果是，这就是基变换的候选。

## 3. 基变换方法

### 3.1 核心操作：升维 → 融合

当多个 sheet 的列结构几乎相同时：

**操作**：
1. 新增一个维度列（如"存货类别"），取值为 sheet 的名称（原材料/半成品/库存商品）
2. 将物理上分散在不同 sheet 的向量，统一复制到同一个 sheet 中
3. 用新维度列来区分来源，而非依赖 sheet 名称

**效果**：
- 原结构：3 个 sheet × 各自公式 = 3 套公式
- 新结构：1 个 sheet × 1 套公式 + 筛选/透视 = **1 套公式**

### 3.2 信息熵的降低

- **变换前**：向量分散在 3 个异构子空间，信息熵高，需要 3 个独立的映射函数（公式）
- **变换后**：向量汇聚在 1 个统一空间，信息熵低，1 个统一的映射函数即可覆盖所有向量

### 3.3 公式坍缩

这是基变换最直接的价值：

| 场景 | 变换前（公式数量） | 变换后（公式数量） | 审计 O 降幅 |
|------|-------------------|-------------------|-----------|
| 3 种存货 × 25 个物料 = 75 个独立公式 | 75 | 1（共用框架，一次拖拽） | A_cog: O(75)→O(1) |
| 12 个月费用报告，每月 1 sheet | 12 套公式 | 1 套公式 + "月份"列 | A_cog: O(12)→O(1) |
| N 个部门相同模板 | N 套公式 | 1 套公式 + "部门"列 | A_cog: O(N)→O(1) |

## 4. 优化协议（7 步法）

当 AI 面对审计工作簿时，按以下步骤执行：

### Step 1：清点（Inventory）

列出工作簿中所有 sheet 的名称、列名、大致行数。

- 如果有文件，运行 `python audit-basis-sense/scripts/analyze_sheet_structure.py <file.xlsx>` 获取结构 JSON
- 如果用户口述，根据描述整理

### Step 2：聚类（Cluster）

将 sheet 按列名相似度分组：

- **完全匹配**：列名完全相同 → 高度候选
- **≥70% 重叠**：多数列相同，1-2 列不同 → 强候选（重叠率 = 公共列数 / min(两方列数)）
- **<70% 重叠**：结构差异大 → 可能不是同一类

### Step 3：识别融合候选（Identify Fusion Candidates）

在每个聚类组内，判断：
- 差异列是否只是"名称类"信息？（如：原材料 vs 半成品 vs 库存商品）
- 合并后是否需要新增维度列？维度列的取值从哪里来？

### Step 4：提出基变换（Propose Transformation）

具体描述：
1. 新增什么维度列？
2. 哪些 sheet 合并为一个？
3. 合并后的统一列结构是什么？
4. 公式如何从 N 套变为 1 套？

### Step 5：估算变换前复杂度

- 需要设置几套公式？
- 每套公式需要几次界面交互（拖拽、复制）？
- 总计审计 O ≈ ?

### Step 6：估算变换后复杂度

- 需要设置几套公式？
- 统一公式框架是否可批量拖拽？
- 总计审计 O ≈ ?

### Step 7：报告收益

用对比格式呈现：

```
变换前：K 个 sheet × M 个公式/sheet → O(KM) 的公式设置 + O(data_rows) 的认知判断
变换后：1 个 sheet × 1 个公式框架    → O(1) 的公式设置    + O(exception_rows) 的认知判断
节省：公式设置从 O(KM) 降到 O(1)，降幅 ≈ KM 倍
```

## 5. 实战案例

### 案例 1：存货计价测试（来自 theory.md）

**原状**：
- 年度计价测试、月度计价测试、月度计价测试汇总
- 每种程序 × 3 种存货（原材料、半成品、库存商品）= 9 张 sheet
- 每种存货抽 25 个物料 × 3 种存货 = 75 个物料
- 每个物料需单独设置公式 → **75 遍公式设置**

**向量空间分析**：
```
原材料年度计价测试 → [原材料明细表, 期初金额, 本期增加, 本期发出, 期末余额]
半成品年度计价测试 → [半成品明细表, 期初金额, 本期增加, 本期发出, 期末余额]
库存商品年度计价测试 → [库存商品明细表, 期初金额, 本期增加, 本期发出, 期末余额]
```
识别：核心列（金额列）完全相同，仅第一列名不同。

**基变换**：
1. 增加"存货类别"列，取值为 原材料/半成品/库存商品
2. 每类程序只需 1 张 sheet，共 3 张（年度计价测试、月度计价测试、月度计价测试汇总）
3. 75 个物料集中在同一个统一框架中，共用 1 套公式
4. 拖动一次即可算出全部 75 个物料的结果

**收益**：
- sheet 数：9 → 3
- 公式设置：75 遍 → 1 遍
- 审计 O：公式设置 O(75)→O(1)，A_cog 不变（仍需判断计价异常）

### 案例 2：多期间费用报告

**原状**：1-12 月费用报告各 1 个 sheet，每个 sheet 相同的列结构。

**基变换**：
1. 新增"月份"列
2. 所有 sheet 合并为 1 个"年度费用报告"
3. 一次性设置公式，通过筛选/透视表分月查看

**收益**：公式设置 O(12)→O(1)

### 案例 3：部门费用分摊

**原状**：N 个部门各 1 个相同模板的 sheet。

**基变换**：
1. 新增"部门"列
2. N 个 sheet 合并为 1 个
3. 一个透视表可以同时看全部分配结果

**收益**：公式设置 O(N)→O(1)

## 6. AI 交互模式

### 6.1 被动模式（用户口述）

用户描述工作簿结构 → AI 应用向量空间模型分析 → 给出优化建议。

**触发语句示例**：
- "我有 3 个 sheet 分别对应原材料、半成品、库存商品，每个 sheet 列基本一样"
- "我每个月有一个 sheet，一共 12 个月，格式一样"

### 6.2 主动模式（用户提供文件）

用户提供 .xlsx 文件 → AI 运行分析脚本 → 解读 JSON → 给出优化建议。

```bash
python audit-basis-sense/scripts/analyze_sheet_structure.py <文件路径>
```

输出是 JSON，AI 负责解读其中的 `analysis_hints.identical_structure_groups`。

### 6.3 引导模式（逐步实施）

用户要求具体操作 → AI 分步指导：

1. "第一步：在这个 sheet 里新增一列，列名叫'存货类别'"
2. "第二步：把所有原材料行的'存货类别'填上'原材料'，依次类推"
3. "第三步：把 3 个 sheet 的数据复制到同一个 sheet"
4. "第四步：选中所有数据区域，用'存货类别'做筛选或透视"
5. "第五步：在第一行写好公式，双击填充柄拖到底"

## 7. 分析工具

本 skill 包含一个可选的 Python 分析脚本：

```bash
python audit-basis-sense/scripts/analyze_sheet_structure.py <path_to_xlsx>
```

**功能**：读取 .xlsx 文件，输出结构 JSON。

**依赖**：`openpyxl`（`pip install openpyxl`）

**输出字段说明**：

| 字段 | 含义 |
|------|------|
| `workbook` | 文件名 |
| `sheets[].name` | sheet 名称 |
| `sheets[].columns` | 列名列表（第一行非空） |
| `sheets[].row_count` | 估算行数 |
| `analysis_hints.identical_structure_groups` | 预计算的相似 sheet 分组 |
| `identical_structure_groups[].common_columns` | 组内共同的列 |
| `identical_structure_groups[].differing_columns` | 各 sheet 独有的列 |

**脚本本身不包含审计逻辑**——它只提取结构，由 AI 用本 skill 的方法论进行解读。

## 8. Gotchas

- **列名有空格/换行**：脚本会自动 trim，但原始列名可能不规范。分析前建议用户确认列名。
- **合并单元格的列头**：openpyxl 读取合并单元格时可能只取左上角的值。如果列名不完整，需要用户手动告知。
- **空 sheet**：空 sheet 没有列名，聚类时会自动忽略。
- **hidden sheets**：openpyxl 会读取隐藏 sheet。如果用户说"只有 N 个 sheet"，但脚本输出更多，检查是否有隐藏 sheet。
- **70% 重叠率不是绝对规则**：聚类结果仅供参考。AI 应结合审计语义判断——即使脚本没聚类在一起，如果语义上属于同一类底稿，仍应提出融合建议。
- **基变换不适合所有场景**：如果多个 sheet 的结构确实完全不同（一个是序时账、一个是科目余额表），则不应强行合并。
- **信息熵不会降到零**：合并后仍需认知判断（检查异常行），审计 O 从 O(N) 降到 O(K)，K 是异常行数，通常远小于 N。

## 9. Troubleshooting

| 症状 | 修复 |
|------|------|
| `ModuleNotFoundError: openpyxl` | `pip install openpyxl` |
| 脚本报 "file not found" | 确认文件路径正确；如果路径含空格，用引号包裹 |
| JSON 中列名为空 | Excel 第一行可能是空行——手动指定数据起始行或清理空行 |
| 聚类结果为空（没有 identical_structure_groups） | 所有 sheet 结构差异都 >20%，可能是确实没有融合机会，也可能是列名不一致（如"金额" vs "金额(元)"） |
| 合并后有重复行 | 确认合并前各 sheet 的维度列值不重叠；必要时增加更多维度列 |
